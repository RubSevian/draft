# MEVIUS2: native Draft specification

MEVIUS2 is discovered in the same way as humanoid and quadruped. All editable
model data is under `src/draft/robots/mevius2/`:

- `parameters.yaml`: geometry, joint limits, motor choices, colors and ordinary
  Draft switches.
- `tree.yaml`: four three-joint legs, expressed with the existing `for_each`
  syntax. Joint axes stay +x/+y on both sides and at the rear.
- `mesh.yaml`: the trunk, generated by the existing loft builder.

The generator, editor, motor solver and fitted coefficients use the upstream
implementation. There is no custom importer/backend and no separate motor
configuration system. See [robot-format.md](robot-format.md) for the format.

## Open and edit

```shell
python scripts/generate_robot.py --robot mevius2 --output-dir generated/mevius2 --fixed-output-dir
python scripts/robot_tuner.py
```

Select **mevius2** in the top row. The ordinary cards expose:

| Card / parameter | Effect |
| --- | --- |
| Link Lengths: `upper_leg_link_length` | Thigh length; initial 0.300 m |
| Link Lengths: `lower_leg_link_length` | Shank length; initial 0.285 m |
| Link Lengths: `hip_abduction_link_length` | Fore/aft roll-to-pitch separation; 0.0625 m |
| Link Lengths: `hip_roll_link_length` | Lateral pitch-to-knee offset; 0.077 m |
| Geometry: `torso_lx`, `torso_ly`, `torso_lz` | Main body dimensions; 0.400 × 0.211 × 0.190 m |
| Geometry: `shoulder_width` | Lateral span between roll axes; 0.160 m |
| Geometry: `hip_mount_x_offset`, `hip_mount_height`, `hip_lateral_offset` | Joint mounting offsets |
| Geometry: `foot_sphere_r`, `foot_x_offset`, `foot_mass_kg` | Foot radius, contact-site offset and mass; 0.030 m, 0.00263 m, 0.120 kg |
| Motor Classes | Assign an actuator class to hip roll, hip pitch and knee |
| Actuator design | Change torque, speed, reduction, power and aspect using native modes |

Changing dimensions rebuilds geometry, inertias and structural masses using
Draft's common rules. **Save as** creates a variant with its own parameter YAML.
The usual feasibility checks can reject dimensions that do not fit the motors.

## Motors

The single `parameters.yaml` starts with three catalogue-backed classes:

| Class | Catalogue entry | Peak torque | Speed | Reduction |
| --- | --- | --- | --- | --- |
| L | RS03 | 60 N·m | 18.85 rad/s (source URDF cap) | 9 |
| M | RS01 | 17 N·m | 28.79793 rad/s | 7.75 |
| S | AK10-9 V2 | 48 N·m | 31.10177 rad/s | 9 |

All joints initially use L. For example, `hip_pitch_mot: M` assigns class M to
all four hip-pitch joints. Class names are identifiers, not a required size order.
All twelve motors are charged once; the belt-driven knee's distal pulley has
zero mass, as in Draft's existing quadruped specification.

To describe another motor, change a class's `<cls>_motor` catalogue name **and**
its explicit torque/speed/gear values together, or omit those explicit values
in YAML to resolve them from the catalogue. Existing explicit values have
priority. The stock interface has class selectors and name text fields; it does
not provide a dropdown of catalogue parts. The editor's table estimates sizing
from the population fit; generation also resolves declared catalogue anchors.
The emitted feasibility report is the source for the final generated masses.

## Relationship to the source URDF

The licensed URDF and 13 STLs in `urdf/mevius2/` remain unchanged. Their original
mass is approximately 22.9065 kg. Automated checks compare the native model's
joint anchors, axes, limits and foot positions against that URDF at several poses.
`BL/BR` source legs map to `rl/rr` in the common naming convention.

This is a **parametric reconstruction**, not a CAD import preserving the source
inertia tensors. The trunk is its main collision box with a slight chamfer;
the small front electronics enclosure is omitted. Legs and motors use the
stock cylinder/sphere primitives. Structural mass, rotor inertia and total mass
are calculated by Draft, so they can differ from the physical source robot.
The stock foot sphere is on the shank axis; its contact site retains the source's
2.63 mm forward offset. Foot bodies/geoms/sites use the common quadruped names.
Hip-roll housings sit inside the torso; their overlap is explicitly allowed by
the same role mechanism used by the stock quadruped and remains reported.
No feasibility gate is disabled for the whole model.

The neutral drawing pose has zero joint angles, as in the source URDF; its knee
zero is outside the source's operating range. Set a bent pose with the ordinary
joint sliders before inspecting a standing configuration. The original controller
uses hip pitch 0.7 and knee −1.2 rad. Physics is the stock editor's passive
simulation; it does not add a pose controller, walking policy or temperature
prediction. The earlier separate import/PD/thermal backend has been removed.

## Controlled simulation and training

`experiments/mevius2.yaml` uses the existing quadruped task with 256 parallel
environments (initial budget for an 8 GB GPU). Logs stay local in TensorBoard;
no W&B account or upload is used. Install the pinned `.[rl]` extra first.

```shell
python scripts/check_robot_rollout.py --config experiments/mevius2.yaml
python scripts/train.py --config experiments/mevius2.yaml
python scripts/play.py --config experiments/mevius2.yaml --checkpoint logs/.../model_999.pt
```

The integration check uses zero actions around the task's nominal stance. It
checks the control/physics pipeline, not walking ability. MEVIUS2 requires its
own trained policy; a policy for another morphology is not evidence of success.
Playback writes `motor_trace.npz` beside the checkpoint on exit.

## Preliminary temperature estimates

The user conditions in `experiments/mevius2_thermal.yaml` are 48 V, ambient 25 °C,
and a duralumin mount. Supply voltage is recorded as context: the chosen
motor torque/speed envelope must correspond to it; this estimator does not
rescale the electrical model from voltage.

```shell
python scripts/estimate_motor_temperature.py --trace logs/mevius2_check/motor_trace.npz
```

The estimate uses the paper's equation (2), `P_loss = tau² * omega_NL / tau_peak`,
and a one-node RC thermal balance. It produces per-joint CSV files and a plot
of the hottest effective module temperature for each cooling scenario. The
thermal resistance values 0.5/1/2 K/W and capacity 450 J/K are **unmeasured
sensitivity assumptions**, not RS03 specifications or confidence bounds.
The result is neither winding-hotspot temperature nor the internal sensor
reading. No idle electronics, gearbox/iron loss, or temperature-dependent
resistance is modeled. A short trace is not automatically repeated to claim a
long-duration walking result. Resets in a recorded rollout count as consecutive
loads without resetting temperature; inspect stability before interpreting it.

Duralumin alone does not determine heat transfer: mount dimensions, contact
area and airflow are needed. Calibrate against a motor heating/cooling test
before treating the curve as a prediction or setting protection thresholds.
